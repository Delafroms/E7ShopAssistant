## 一、红队 3 条待调通用例：修好了

根因是**编排器（Attacker）与引擎状态机不同构**：它用"历史上点过行内购买"这个**粘滞标志**
决定返回什么画面，于是引擎一点过购买，画面就永久是弹窗 → 引擎在 SCAN 阶段看到弹窗 →
进 RECOVER 循环 → 断言全部误报。

修法：按「弹窗**此刻**是否还开着」驱动 —— 点过行内购买且之后没被取消 → 开着；
RECOVER 点过取消 → 关上；确认点过之后按攻击场景决定关/不关。

另外两处断言修正（都是我的断言错，不是引擎错）：
- **handled 会被刷新清空**（设计如此："刷新后重新给机会"）→ 断言"是否曾标记过某行"必须看**历史**；
- 超时**保守计数**是设计行为 → 断言改为"必须写 UNCONFIRMED、**绝不写 PURCHASE COMMIT**"。

**现在红队 5 条全绿**，其中最有价值的一条是**封顶行为的正面证据**：
价格歧义（两条相同的期望价）→ 引擎连续 VERIFY FAIL → 第 3 次出现
"VERIFY FAIL x3 … -> 暂时放弃该行（刷新后重置，避免反复锤同一个按钮）" ✓

## 二、AI 管线（AiBotEngine）FSM 测试补齐

两处可测性改造（**生产行为不变**）：
1. `AiBotEngine(host, generation, vision: RecognitionEngine = YoloEngine())` —— 视觉引擎可注入；
2. `YoloDet.loaded` 改 `internal set`（让测试能模拟"模型已加载"，生产无其它写入点）。

三条用例：
- **模型未加载 → 明确报错并退出，绝不降级成传统点击**（AI 管线的立身之本）；
- **零感知 → 一次都不点、不滑动**（宁可不动也不猜）；
- **收到停止请求 → 立即退出**。

至此两条点击管线都有 FSM 整机测试约束 —— 正是"双管线各自演化"这个系统性风险的对策。
