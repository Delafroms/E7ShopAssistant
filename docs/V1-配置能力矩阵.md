# V1 配置能力矩阵（D4 审计报告）

> 审计口径：**每一个用户能改的设置，都必须同时满足三条** ——
> ① 有入口（UI 能改）② 有读者（运行时真的有代码在读它）③ 可验证（改了以后有可观测的行为变化）。
> 任何一条不满足的，要么补上，要么删掉；**不允许留"看得见改不动"的假开关**。
>
> 审计方法：把 `AppConfig` 的全部字段反向扫一遍"谁在读"，再把 `SettingsSchema` 与各主题的设置 UI
> 正向扫一遍"谁能改"，两个方向的差集就是问题清单。审计日期：V1 冻结期（versionCode 15）。

## 二、本轮删除的 4 个死配置（附证据）

| 字段 | 为什么是死的 | 处理 |
|---|---|---|
| `minGold` 金币保护下限 | 闸门条件是 `cfg.minGold > 0 && session.startGold > 0 && …`，而**三个启动入口全部传 `startBot(0, 0)`**（`ShopAccessibilityService:1142`、`Themes.kt:480/636/1653`），`startGold` 恒为 0 → 闸门永久短路。旧版 UI 项（`gold_floor`）此前已移除，字段与引擎里的死分支还留着 | 删字段 + 删两套引擎的死闸门 + 删 `Host.errGoldFloor()` + 删 `err_gold_floor` / `gold_floor` 双语文案 |
| `gpuFps` GPU 识图帧率 | GPU 引擎已从架构中移除，全代码库无人读取 | 删字段 |
| `pageAnim` 页面切换动画 | 字段与双语文案（`page_anim`）都在，但**功能从未实现**：`Themes.kt` 没有任何页面过渡动画代码，NavHost 也没接线 | 删字段 + 删双语文案 |
| `wdAutoSync` WebDAV 自动同步 | 无 UI、无读者；且在没有冲突解决（D3）之前，自动同步会用旧记录覆盖较新记录 | 删字段；功能与 D3 一起列入 V1.1 |

> 金币下限保护并没有消失，只是**换成真正生效的那一个**：`goldSpendCap`（金币消耗上限）。
> 真正的"金币余额下限"需要能读到当前金币（启动时输入或 OCR 读金币数），列入 V1.1。

## 三、刻意"有配置、无 UI"的项（不是漏做，是设计决定）

| 字段 | 为什么不暴露 |
|---|---|
| `swipeCenterX` / `swipeTopY` / `swipeBottomY` | 这是**滑动几何**（翻页手势路径），不是点击目标。新架构所有点击点都来自识别层 bbox 中心，而滑动几何是随屏幕尺寸换算的自适应参数——暴露给用户只会制造误配置 |

## 四、反向审计：孤儿字符串（已知、未处理）

把 `res/values/strings.xml` 的全部 243 条与代码/布局里的引用做差集，发现 **84 条已无人引用**的死字符串，全部是旧架构残留，例如：

- 旧引擎名：`ocr_engine_builtin` / `ocr_engine_gpu` / `ocr_engine_opencv` / `gpu_capture` / `gpu_capture_note`
- 旧模板匹配：`tpl_drag_hint_bookmark` / `tpl_drag_hint_medal` / `tpl_saved` / `tpl_too_small` 等 8 条
- 旧设置页：`save_bot` / `save_humanize` / `save_appearance` / `anim_settings` / `top_logo` / `bg_hint` 等
- 旧风险弹窗：`risk_title` / `risk_notice`（现行用的是 `dlg_risk_title` / `dlg_risk_msg`）

另有 `appearance_m3` 只有英文、缺中文翻译。

**处理决定：本轮不删。** 理由：这些字符串用户完全不可见，删除对玩家零收益；而 84 条批量删除属于"大范围但低价值"的改动，混在 V1 冻结期里只会放大回归面。建议放进 V1.1 清理轮一次性处理（清单已在上方分类列出）。

## 五、这套矩阵怎么被守住

配置生效与否靠人肉点一遍不可持续，因此配套了**双引擎识别回归台**：

```
tools\benchmark_run.ps1 -Tag <标记>            # 默认断言 yolo 引擎
tools\benchmark_run.ps1 -Tag <标记> -Engine traditional
```

App 侧一次基准会把**两套引擎都跑一遍**（报告 `engines[]`），输出召回率 / 误检 / 均值 / 中位 / P95 / 极值，
并落地成 JSON 供脚本断言与归档。之所以要两套都跑，是因为旧版只测"当前配置的引擎"——
手机上只要残留一次 `traditional` 设置，就会拿传统引擎的数字去对比 YOLO 基线，结论完全失真（实测踩过一次）。

当前基线（14 张样本）：

| 引擎 | 召回 | 误检 | 均值 | 中位 |
|---|---|---|---|---|
| yolo（默认） | 100.0% | 3 | 481ms | 543ms |
| traditional | 92.9% | 3 | 477ms | 541ms |

传统引擎的缺口是**已知且有明确归因**的：`medal_partial_top.jpg`（顶部被滑到半截的行）它一个候选都给不出，
因为它的候选全部锚定在"能读到的商品名文本"上；YOLO 直接看图标本身，所以不受影响。其余 13 张两套引擎结果完全一致。
